# PLAN: Between-subjects (unpaired) support for `compare()`/`analyze()`

## 1. Problem statement

`evalstats.compare()`/`analyze()` assume every compared entity was scored on the *same* set of items: `evalstats/core/types.py`'s `BenchmarkResult` is fundamentally an `(N_templates, M_inputs, ...)` dense array, built by `evalstats/io.py`'s `from_dataframe()` pivoting a long dataframe on a shared item column. `evalstats/core/paired.py`'s entire pairwise engine (`all_pairwise`, `PairwiseMatrix`, `pairwise_differences`, `PairedDiffResult`) is built around `per_input_diffs` — item-*matched* differences — and the router (`evalstats/core/router.py::_analyze_single`) hard-raises if the pivoted matrix has any missing cells (`ValueError: scores contain N NaN (missing) cell(s)... not supported by the bootstrap analysis path`).

This is correct and necessary for within-subjects designs (prompt/model comparisons on a shared benchmark) but has no valid, *statistically appropriate* path for genuinely between-subjects data — e.g. comparing several competitor apps' user reviews, where each app's reviewers are disjoint and there is no shared "item" at all. (Note, corrected after review: `compare()` already calls `from_dataframe(..., strict_complete_design=False)` in all its dispatch paths, so genuinely disjoint per-group item IDs *do* pivot into a matrix with NaN cells without any fabrication — the synthetic-positional-item-index trick is specifically needed to dodge the bootstrap path's `has_missing` hard-raise, not to satisfy `from_dataframe` itself. See §2.1a for why the codebase's own suggested escape hatch, `method="lmm"`, doesn't actually solve this either.) Forcing the data through via the item-index hack makes the bootstrap path run without erroring, but it silently runs a *paired* test (differencing item #7 of group A against item #7 of group B) on data with no such correspondence — statistically invalid, not merely inelegant.

Independently, `evalstats/tests/__init__.py` already contains real, PPI-corrected, between-subjects test functions (`ttest`, `mannwhitney`, `anova_oneway`, `kruskalwallis`) that operate correctly on ragged, unaligned group arrays. But they are low-level, unergonomic (no `factors=`/`metric=`, no design auto-detection, manual dataframe splitting required) and have **no `.summary()`/`.plot()` reporting layer** — `TestResult` is a bare dataclass. This plan scopes closing that gap. **Scope correction after review**: this plan does *not* aim for full `compare()`-quality parity (executive summary, critical-difference rank bands, forest-plot brackets) — see §3.6 and §4 for exactly what it does ship (per-group means with gradient CIs + a flat, FWER-controlled pairwise table), which is a real but smaller deliverable than "a `compare()`-quality entry point" implies.

## 2. Current-state findings

### 2.1 Verification of the "already exists" claims

All confirmed correct, with refinements:

- **`kruskalwallis`'s pairwise post-hoc** (`_ppi_kruskal_wallis_pairwise`, `:1371`) is real and does compute a joint-bootstrap-covariance Wald omnibus test plus a per-pair θ̂_ab (`extra["pairwise_effects"]`, populated at `:5055`). Confirmed.
- **Important refinement**: `extra["pairwise_effects"]` is *only* populated when `groups_lab is not None` (line `5027: if groups_lab is not None:`). **There is currently no pairwise post-hoc at all for the uncorrected (no-PPI) k≥3 case** — a between-subjects HCI researcher without an LLM judge in play today gets nothing from `kruskalwallis()` beyond the omnibus H/p. This is a concrete new-code gap, not just a UX one.
- **`_detect_paired`** (`evalstats/labeling.py:72`) is exactly as described: 90%-of-universe item-overlap heuristic, used by `detect_design`/`sample_for_labeling` for the `evalstats label` CLI. Confirmed it lives only in `labeling.py`, imported nowhere from `core/` or `api.py`.
- **No plotting/summary layer for `evalstats.tests`**: confirmed — `TestResult` has no `.plot()`/`.summary()` beyond a plain text `.summary()` printer (line ~130 area) that is not the gradient-CI machinery `core/summary.py` has for `compare()`.
- **Additional finding not previously flagged**: `evalstats.tests._run_alignment_report` (`:470`) *already* wraps raw arrays in a minimal `EvalResults` stub and calls the real `evalstats.alignment.judge_alignment()` (not a separate reimplementation) — so the "disclosure/representativeness-check machinery" from `alignment.py` is *already* plugged into every `evalstats.tests` PPI call. This narrows what Phase work is actually needed there to "surface it in a compare()-shaped result object," not "wire it up."

**2.1a. Considered and rejected: `method="lmm"` as an existing escape hatch.** `_analyze_single`'s own `has_missing` error text (`core/router.py:990-996`) explicitly suggests `method='lmm'` for incomplete designs, and tracing it confirms `method="lmm"` is checked *before* the `has_missing` raise, bypassing it entirely by fitting `score ~ C(template) + (1|input)` via `statsmodels.MixedLM`. This is not a viable substitute for this plan, for three reasons: (1) it has no PPI/rectification wiring at all — the entire point of this package's between-subjects extension; (2) with genuinely disjoint items, every item is a singleton under the `(1|input)` random effect, which is statistically degenerate (a random-effects term needs repeated observations per level to estimate variance); (3) it produces neither the θ_ab dominance-probability framing nor the HCI-conventional nonparametric tests this plan (and the user's explicit KW/MWU direction) call for. Recorded here so the "why not just use the existing LMM path" question has an on-the-record answer.

### 2.2 Answers to the three open questions

**Q1 — Are `kruskalwallis`'s per-pair CIs already FWER/simultaneous-corrected?**

**No — confirmed marginal (alpha-level), not simultaneous.** In `_ppi_kruskal_wallis_pairwise` (`evalstats/tests/__init__.py:1371`), both the `power_tune=True` and `power_tune=False` branches build `ci_lo`/`ci_hi` via:
```python
ci_lo = np.percentile(boots, 100 * alpha / 2, axis=0)
ci_hi = np.percentile(boots, 100 * (1 - alpha / 2), axis=0)
```
using the *raw* `alpha` passed straight through from `kruskalwallis(alpha=0.05, ...)` (`:4905`, forwarded unmodified at `:5043`) — no Šidák/Bonferroni/Romano-Wolf adjustment across the `C(k,2)` pairs the way `core/paired.py::_simultaneous_cis_router` (`:1947`) does for the paired path. The omnibus Wald test *does* correctly use the full joint bootstrap covariance (so the omnibus p-value is fine), but if the per-pair CIs were surfaced in a pairwise grid the way `compare()`'s tables do, they would overclaim precision/significance under multiple comparisons — exactly the concern flagged. **This materially changes the plan**: before a between-subjects `compare()`-analog can show a pairwise table with k≥3 groups, it needs a family-wise-corrected version of this per-pair CI, decoupled from the omnibus scalar-effect CI which should stay at nominal `alpha` (they currently share one `alpha` parameter — needs splitting).

**Decided after review: ship Bonferroni (`alpha/n_pairs`), not Šidák, for this correction.** Šidák's exactness relies on independence (or positive-orthant dependence) between the pairwise statistics; `_ppi_kruskal_wallis_pairwise`'s own docstring notes the pairwise θ estimates are correlated (pairs sharing a group draw from the same resample) — likely favorable for Šidák, but unproven for this specific estimand, and this codebase has never simulated it. Bonferroni's union-bound guarantee holds unconditionally regardless of that dependence structure, needs zero unverified assumptions, and is a one-line difference in the adjustment formula (`alpha/k` vs. `1-(1-alpha)**(1/k)`). Given this plan's own standard elsewhere is "don't ship unvalidated statistical machinery silently," Bonferroni-now/Šidák-later (once a calibration sweep exists) is the correct sequencing, not a placeholder to fix later.

**Q2 — Reconciling θ_ab (stochastic dominance) vs. mean-difference reporting.**

Resolved by a concrete codebase finding: **`anova_oneway` (`:4552`) has no pairwise post-hoc breakdown at all** — its `corrected_estimate` is a single scalar ("weighted between-group variance"), unlike `kruskalwallis`'s per-pair `extra["pairwise_effects"]`. So for k≥3 groups, **Kruskal-Wallis's θ_ab dominance-probability post-hoc is currently the *only* validated multi-group pairwise mechanism in the codebase, for any score type** — building a PPI-corrected ANOVA analog (e.g. a Tukey-HSD-style joint-bootstrap mean-difference post-hoc) would be genuinely new, unvalidated statistical work, not routing. Recommendation (see §3.2): don't try to force a false k≥3 mean-difference default — accept θ_ab as the k≥3 headline effect for *all* score types, and reserve mean-difference reporting (via `ttest`) for the k=2 case where a validated closed-form PPI mean-difference path (`_ppi_two_sample_t_interval`, `:2589`) already exists. Report both estimand kinds side by side rather than picking one as canonical, with clear labeling so a reader isn't confused about which comparisons come from which family (θ table only appears at k≥3; a mean-difference table only appears at k=2, or optionally in addition at k≥3 if a user explicitly opts into pairwise `mannwhitney`/`ttest` calls run independently — flagged as *not* simultaneously FWER-controlled with the KW-based table if done that way).

**Q3 — Do the paired and unpaired PPI implementations share enough to unify?**

**Shared**: the low-level PPI primitives in `evalstats/ppi.py` (`correct`, `PPIResult`, `_analytic_mean_correct`, `_adaptive_shrink_lambda`, `_lambda_var_inflation`, `_analytic_logit_t_correct`, etc.) — confirmed via grep, `evalstats/tests/__init__.py` imports these directly throughout (~40 call sites) and uses the exact same rectifier/power-tuning machinery `evalstats.api._run_alignment_ppi` uses.

**Not shared, and shouldn't be forced to be**: the *dispatch/orchestration* layer. `api.py::_run_alignment_ppi` (`:1414`) is built around `all_pairwise()`'s item-aligned `PairwiseMatrix` output and its own dispatch tables (`_ppi_pairwise_dispatch` `:931`, `_ppi_robustness_dispatch` `:1378`) that fundamentally assume a dense `(N, M)` matrix with `per_input_diffs`. `evalstats/tests/__init__.py` has its own, separate label-sanitization (`_sanitize_ppi_labels` `:510`, `_sanitize_multigroup_ppi_labels` `:2799`) and rectifier constructions built for raw ragged group arrays. Trying to unify these would mean rewriting one to fit the other's item-alignment assumption, which is exactly the wrong direction for this feature. **Recommendation**: the between-subjects `compare()`-analog should call `evalstats.tests`' existing `ttest`/`mannwhitney`/`kruskalwallis`/`anova_oneway` directly as its statistical engine (a thin orchestration layer on top), not attempt to route through `_run_alignment_ppi`.

### 2.3 Additional architecturally-relevant findings

- **`AnalysisBundle`/`BenchmarkShape`/`PairedDiffResult` are structurally incompatible with between-subjects data**, not just conventionally so: `PairedDiffResult` (`evalstats/core/paired.py:162`) carries `per_input_diffs: np.ndarray  # shape (M,)`, and its `rank_biserial`/`wilcoxon_p` properties are computed *from* that array. There is no way to populate this for two groups with no item correspondence. A between-subjects result needs a **sibling** dataclass (e.g. `GroupDiffResult`) carrying `group_a_scores`/`group_b_scores` (or just summary stats + the raw θ̂/mean-diff + CI), not a subclass or a coerced instance of `PairedDiffResult`.
- **`evalstats.quick.summarize`/`mean_ci`** (`evalstats/quick.py:98`, `:258`) are a major, underused building block for this feature: `summarize(df, factor=..., metric=...)` already computes per-group **marginal** mean+CI *independently per group* (own auto-detected data kind, own N — no rectangular-design requirement at all, confirmed at `:280-283`'s docstring and the per-group loop at `:382-392`). This is exactly the per-entity display a between-subjects `.summary()` needs for its "mean per group" section. The only gap: it hardcodes `multi_ci=False` (`:391`) when calling `robustness_metrics()`; `robustness_metrics()` (`evalstats/core/variance.py:223`) already supports `multi_ci=True` (populates `RobustnessResult.multi_ci`, `:91`) — a one-line-per-call-site change to unlock gradient CI bands for between-subjects groups too.
- **`core/summary.py`'s low-level renderers are decoupled from `PairwiseMatrix`/`AnalysisBundle`**, confirmed: `_gradient_interval_line` (`:2172`) and `_ascii_interval_line`/`_choose_interval_line` (`:2277`) take plain floats (`mean`, `multi_ci: dict[float, tuple[float,float]]`, `spread_low/high`, `axis_low/high`) — no bundle object required. These *are* directly reusable for a between-subjects summary layer. What is *not* reusable without real adapter work is the higher level: `_print_pairwise_section` (`:1023`), `_print_executive_summary` (`:3140`), `_assign_significance_groups`/`_critical_difference_groups` (`:2762`/`:2568`) all read `PairwiseMatrix`/`AnalysisBundle` fields directly, and `evalstats/vis/forest.py::plot_ci_forest` (`:466`) duck-types against `ComparisonResult`'s full interface (`.labels`, `.entity_stats` — SimpleNamespace built from `RobustnessResult`, `.pairwise`, `.alpha`, `.as_view` — see `api.py:299-360`). Building a between-subjects object that's forest.py-compatible is plausible for the "means + per-group CI" half but nontrivial for the pairwise-significance half (needs a `PairwiseMatrix`-shaped adapter around KW/MWU results).
- **`ComparisonResult`** (`api.py:38`) wraps `AnalysisResult` (`AnalysisBundle | MultiModelBundle | dict`) exclusively; there is no union branch for a between-subjects result today, and its many `@property`s (`entity_stats`, `pairwise`, `unbeaten`, `to_dict`/`to_frame`) all read bundle-shaped fields. A between-subjects-aware version needs either (a) a new sibling class (`GroupComparisonResult`) with its own `.summary()`/`.plot()`/`.to_dict()` implementing the *same external surface* where sensible, or (b) teaching `ComparisonResult` to hold a `Union[AnalysisResult, UnpairedResult]` and branch internally in every property. (a) is far less invasive and matches how `MultiModelBundle` was added as a genuinely different shape rather than shoehorned into `AnalysisBundle`.
- **`evalstats/loader.py::_detect_score_type`** (`:45`) taxonomy is `Literal["binary", "continuous", "likert", "grade"]` — note this is a *different* taxonomy from `core/config.py::AUTO_ANALYZE_METHOD_TABLE`'s `data_kind` (`"binary"`, `"bounded_01"`, `"likert"`, `"unbounded"`, resolved in `router.py::resolve_auto_robustness_method` `:762`). `"grade"` (0–100 integers) has no direct `data_kind` analog unless a `score_range=(0,100)` is supplied — this mapping gap needs an explicit decision in the between-subjects routing table too, not just inherited silently.
- **The paired path's `method="auto"` is *not* "nonparametric by default"** — worth confirming explicitly since the prompt's phrasing implied it might be. `AUTO_ANALYZE_METHOD_TABLE` (`config.py:120`) routes by data kind to closed-form, distribution-appropriate estimators (Bayesian-paired/Tango for binary, logit-t for bounded continuous, NIG for likert, t-interval for unbounded) — none of these are rank-based/nonparametric tests. So "mirror the paired path's spirit" and "nonparametric-by-default per HCI convention" are two different, sometimes-conflicting philosophies, not the same thing restated. See §3.2 for how this plan reconciles them.

## 3. Proposed architecture

### 3.1 Design-detection: where `_detect_paired` should live

Promote the design-detection logic out of `labeling.py` into a new leaf module, `evalstats/core/design.py`, with zero dependencies beyond `pandas`/`numpy` (mirrors how `bundles.py` was split out specifically so `router.py` and `summary.py` could share types without a circular import — same rationale applies here for `labeling.py` and `api.py`/`core/router.py`, which currently have no dependency on each other and shouldn't gain one directly). Move `_detect_paired` (and the useful bits of `detect_design`'s pairing logic) there as a public `detect_paired(df, factor_col, item_col) -> bool`, keep `labeling.py::_detect_paired` as a thin re-export for backwards compatibility (or update its one call site directly — it's only used internally). `evalstats.api.compare()` imports it from the same place `labeling.py` does, so there is exactly one implementation.

### 3.2 Routing: `compare()`'s auto-detection and the k=2/k≥3 × score-type decision table

`compare()` (`api.py:2308`) already resolves `item_col`/`factor_col_name` and has the raw `df` in hand before it calls `from_dataframe`. Insert a `detect_paired(df, factor_col_name, item_col)` check right there, per dispatch path (model/prompt/arbitrary-column — paths A/B/C at `:2556`/`:2616`/`:2670`). When `False`:

- Route to a new function, `_compare_unpaired(df, factor_col_name, item_col, metric_col, alpha, alignment, engine_kwargs, ...)`, living in a new module `evalstats/core/unpaired.py` (parallel to `paired.py`), rather than trying to thread unpaired logic through `analyze()`/`_analyze_single` — those are structurally paired-only (`has_missing` raises, `pairwise_differences` assumes item correspondence) and should not be made to branch internally; a sibling code path is both safer and matches how `analyze_factorial()` already exists as a separate LMM entry point rather than a branch inside `_analyze_single`.
- `_compare_unpaired` groups `df[metric_col]` by `df[factor_col_name]` into ragged arrays (mirroring `evalstats.quick.summarize`'s DataFrame path exactly, `quick.py:312-334` — reuse that grouping code rather than re-deriving it), resolves `k = n_groups`, and dispatches into **two families, decided (not open) after discussion**:

  **Binary data (both k=2 and k≥3): `anova_oneway` (omnibus) + repeated pairwise `ttest` (Welch's) post-hoc.** Not Kruskal-Wallis/Mann-Whitney. Rationale: the textbook-correct test for comparing proportions is chi-square/Fisher's exact, but neither has any PPI correction machinery in this codebase, and deriving one would be new, unvalidated statistical work — exactly what this plan avoids elsewhere. Treating a 0/1 outcome as a numeric mean and reusing the already-validated `ttest`/`anova_oneway` PPI paths (the "linear probability model" approach, well-precedented in applied statistics) gives Δp (proportion difference) with a CI — the effect size a reader actually expects for a binary outcome — using entirely existing, validated machinery, and keeps the same effect-size language at k=2 and k≥3 (no framing switch as k grows). **Explicit acknowledged limitation, not hidden**: t-intervals on binary/bounded data can produce CIs outside [0,1]/[-1,1] at extreme proportions or small N — exactly why the *paired* path uses Tango/Bayesian-binary instead of a generic t-interval for binary data, and there is no between-subjects equivalent of Tango today. This is a deliberate patch, not a clean solution — flagged for a specific boundary-behavior check in Phase 1's calibration testing (see §4), not something to discover post-hoc.

  **All other score types (continuous, likert, grade), both k=2 and k≥3: `kruskalwallis` (omnibus + θ_ab pairwise post-hoc), with `mannwhitney` as the k=2 special case** (Kruskal-Wallis reduces to Mann-Whitney at k=2, so this is one family, not two). Reports θ_ab = P(a>b), not a mean difference — less immediately interpretable for continuous data than Δmean would be, but avoids needing a second validated parametric pairwise construction (a Tukey-HSD-style joint-bootstrap mean-difference post-hoc doesn't exist in this codebase and would itself be new, unvalidated work — see Q2 in §2.2). `anova_oneway` remains available as an **omnibus-only** alternative for continuous data specifically (its own scalar effect size), not part of the pairwise table.

  **`"grade"` score type**: treat as `continuous` for this routing table (closest existing behavior — `_detect_score_type` already treats plain integer 0–100 data distinctly from likert 1–10, and grade data is usually intended as interval-scaled, e.g. exam percentages) — flag as an assumption needing eventual real-data validation, not silently inherited.

This table should live in `evalstats/config.py` as a new `AUTO_UNPAIRED_METHOD_TABLE` (mirroring `AUTO_ANALYZE_METHOD_TABLE`'s `(data_kind, ...) -> method` shape, keyed additionally by `k == 2` vs `k >= 3`), so it's inspectable/testable the same way, and so the "reason" strings convention (which this codebase clearly values — every existing table row has one) carries over. Note the table now has exactly two rows in practice (binary → `anova_oneway`/`ttest`; everything else → `kruskalwallis`/`mannwhitney`), not four — simpler than the original draft.

**Synthetic-item-column fallback (added after review).** Some between-subjects datasets have no natural per-row identifier at all (e.g. just `app` + `rating`, no reviewer ID) — `compare()` currently hard-errors (`EvalLoadError`) before any of the above is reached, since item-column resolution happens unconditionally first and does not fabricate one. `labeling.py::_resolve_columns` already solves exactly this with a `SYNTHETIC_ITEM_COL = np.arange(len(df))` fallback; port the same fallback into `compare()`'s unpaired path so datasets with no item column don't hit a wall before `detect_paired()` is ever consulted. Small, but required for Phase 1, not optional — without it, some of the exact between-subjects datasets this plan is meant to unblock still error out.

### 3.3 PPI integration

`_compare_unpaired` receives `alignment=` (a dict of human-label columns, mirroring `compare()`'s existing `alignment=` kwarg) and, when present, splits the human-label column the same way it split the metric column (by `factor_col_name`), producing the `groups_lab=`/`a_lab=`/`b_lab=` arrays `evalstats.tests` functions expect, then calls them with those. No new PPI machinery is needed for the k=2 and PPI-present k≥3 cases — they already work end to end (`ttest`/`mannwhitney`/`kruskalwallis` with labels). The one required addition (§3.4) is the FWER-correction gap for k≥3 pairwise CIs, and (§3.5) the currently-missing uncorrected (no-PPI) k≥3 pairwise post-hoc.

### 3.4 Multiple-comparison correction for the between-subjects pairwise table (resolving Q1) — two axes, mirroring the paired path

The paired path already separates two independent corrections: a simultaneous-CI construction (Šidák/joint-bootstrap) and a *separate* p-value correction (Shaffer/Romano-Wolf). The between-subjects pairwise table should follow the same two-axis structure, applied uniformly to **both** families from §3.2 (the Kruskal-Wallis θ_ab family and the binary anova_oneway/ttest Δp family — both produce a `C(k,2)`-sized family of pairwise comparisons that need the same correction treatment):

- **CI axis: Bonferroni** (`alpha / n_pairs`), not Šidák. Šidák's exactness relies on independence (or positive-orthant dependence) between the pairwise statistics; the pairwise estimates here are correlated (pairs sharing a group draw from the same resample) — likely favorable, but unproven for this estimand, and this codebase has never simulated it. Bonferroni's union-bound guarantee holds regardless of that dependence structure, needs zero unverified assumptions, and is a one-line difference in the adjustment formula. Šidák deferred to a later, validated phase (§4, Phase 2).
  - For the Kruskal-Wallis family: split `kruskalwallis`'s single `alpha` into the omnibus-CI alpha (unchanged, nominal) and a Bonferroni-adjusted pairwise-table alpha; call the private `_ppi_kruskal_wallis_pairwise` (already computes the right joint-bootstrap covariance) directly with the adjusted alpha, rather than changing `kruskalwallis()`'s own public contract.
  - For the binary family: call `_ppi_two_sample_t_interval` (or the non-PPI two-sample t-interval) once per pair with the same Bonferroni-adjusted alpha.
- **p-value axis: Holm** (new addition, decided after discussion — not Bonferroni here). Holm is a step-down p-value procedure, not a CI construction — it doesn't have a closed-form "widen the CI" rule the way Bonferroni/Šidák do, so it's the wrong tool for the CI axis above, but it's the *right* tool for a separate per-pair p-value correction: uniformly more powerful than Bonferroni (rejects at least as many true effects, often more) while still exactly controlling FWER, with no extra assumptions. This is a cheap reuse, not new code: `evalstats/core/stats_utils.py::correct_pvalues(method="holm")` already exists (used elsewhere this session for the representativeness-check corrections) — apply it to the family of per-pair p-values from whichever test family is in play.
- Both corrections are simple enough (a scalar multiply for Bonferroni, an existing off-the-shelf step-down function for Holm — no new bootstrap machinery, no new dependence assumptions) that they ship in the same phase as the rest of the pairwise table, not as a deferred follow-up — see the merged Phase 1 in §4.

### 3.5 Uncorrected (no-PPI) k≥3 pairwise post-hoc — new code, small, both families

Since `kruskalwallis()` only populates `pairwise_effects` under PPI, add a small non-PPI analog for the Kruskal-Wallis family: a joint bootstrap of `_kw_pairwise_thetas` (`evalstats/tests/__init__.py:1271`, already label-independent) across all `C(k,2)` pairs from one shared per-group bootstrap draw, Bonferroni/Holm-corrected the same way as §3.4. This is structurally a stripped-down copy of `_ppi_kruskal_wallis_pairwise` with the rectifier terms removed. For the binary family, the non-PPI analog is simpler still: ordinary (`scipy.stats.ttest_ind`-equivalent) pairwise Welch's t-intervals, same correction. Both are small, mechanical, low risk, but still new code needing their own tests. Live in `evalstats/core/unpaired.py`, not `evalstats/tests/__init__.py` (keeps `evalstats.tests` scoped to "PPI-corrected wrappers for common statistical tests" per its own module docstring, `:1`).

### 3.6 Result object and reporting layer

New `GroupComparisonResult` class in `evalstats/core/unpaired.py` (or `evalstats/api.py` alongside `ComparisonResult` if preferred for discoverability — lean toward `core/unpaired.py` to keep `api.py` from growing further, with `api.py` importing and re-exporting it), holding:
- Per-group `GroupSummary`-shaped stats (reuse `evalstats.quick.summarize`'s grouping + `robustness_metrics(multi_ci=True)` per group, per §2.3's finding — this gets gradient-CI bands "for free").
- The omnibus `TestResult` from the appropriate `evalstats.tests` function.
- The pairwise table — θ_ab + Bonferroni-corrected CI + Holm-corrected p-value (continuous/likert/grade family), or Δp + Bonferroni-corrected CI + Holm-corrected p-value (binary family) — as a new `GroupDiffResult` list (not `PairedDiffResult` — no `per_input_diffs`), consistent across k=2 and k≥3 within each family.
- `.summary()`: a new printer in `core/summary.py` (or a new `core/summary_unpaired.py` to avoid bloating the already-3500-line file further) that reuses `_gradient_interval_line`/`_choose_interval_line` directly (confirmed reusable, §2.3) for the per-group means row and writes its own, simpler pairwise section (no need to replicate `_print_pairwise_section`'s full paired-specific logic — e.g. no Wilcoxon/rank-biserial/agreement-MCC columns, which don't apply here).
- `.plot()`: **do not** attempt full `plot_ci_forest` duck-type compatibility in the first phase (§2.3 flagged this as nontrivial — needs a `PairwiseMatrix`-shaped adapter). Ship a small bespoke matplotlib function (`evalstats/vis/forest_unpaired.py` or a `kind="unpaired"` branch inside `forest.py` if the group-means-only rendering path turns out to overlap enough) that draws per-group point + gradient CI, which is the 80% use case for the paper's App Store example. Full forest.py parity (pairwise significance brackets, `as_view`, etc.) is a stretch goal, not MVP.
- **Alignment disclosure placement (added after review)**: `GroupComparisonResult.summary()` prints the judge-alignment/representativeness report inline, in the same position and style as the paired path's pink banner (`core/summary.py`'s existing `_print_bundle_summary` PPI block) — automatically whenever `alignment=` was passed, not as a separate opt-in step. Since `_run_alignment_report` already calls the real `judge_alignment()` (§2.1), this is a rendering call, not new alignment logic.

## 4. Phased implementation plan

**Revised after review**: the original Phase 1/2 split shipped a k≥3 pairwise table in Phase 1 that was honestly marked non-simultaneous — not a real milestone, since the paper's own motivating scenario (comparing several competitor apps) is exactly the k≥3 case, and a "final" chart with visibly uncorrected CIs isn't something to publish from. Since the FWER fix turned out to be simple (Bonferroni, no new bootstrap machinery — see §3.4), there's no reason to ship it separately. Phases 1 and 2 below are merged into one shippable, honestly-complete unit.

**Phase 0 (must-have, prerequisite, ~half day).** Move `_detect_paired` into `evalstats/core/design.py`; re-export from `labeling.py` unchanged. No behavior change. Add a unit test asserting `labeling.py`'s existing paired-detection tests still pass unmodified plus a new direct import test.

**Phase 1 (must-have — merged, the real "smallest complete deliverable").** New `evalstats/core/unpaired.py`:
- `_compare_unpaired()` dispatcher implementing §3.2's two-family routing table (as `AUTO_UNPAIRED_METHOD_TABLE` in `config.py`: binary → `anova_oneway`/`ttest`; everything else → `kruskalwallis`/`mannwhitney`), for the single-factor case only (mirrors `compare()` paths A/B/C, *not* factorial/multi-model — explicitly out of scope, see §6). Includes the synthetic-item-column fallback (§3.2) so datasets with no natural item identifier don't hard-error before this code is ever reached.
- `GroupComparisonResult` + `GroupDiffResult` dataclasses (§3.6), **with Bonferroni-corrected simultaneous CIs and Holm-corrected p-values for the pairwise table from day one, for both families** (§3.4/§3.5, PPI and non-PPI variants) — no interim "marginal CI with a warning" state; this ships correct or doesn't ship.
- `to_dict()`/`to_frame()` on `GroupComparisonResult`, matching `ComparisonResult`'s shape closely enough for downstream tooling — moved into Phase 1 (confirmed load-bearing: evalstats is a library API, programmatic export matters as much as printed output).
- **`compare(..., design="auto"|"paired"|"unpaired")` explicit opt-in, decided after review — not silent auto-routing.** `design="auto"` (the default) preserves 100% of today's behavior: if the data pivots cleanly (paired), nothing changes. If it doesn't, and `detect_paired()` says the data looks genuinely unpaired, **raise a clear, actionable error** ("this looks like a between-subjects design — pass `design=\"unpaired\"` to confirm") rather than silently switching statistical engines. The `_detect_paired` 90%-overlap heuristic was validated for a lower-stakes decision (which *sampling* strategy the `evalstats label` CLI uses) — reusing it to silently decide *which statistical engine runs* on existing users' data is a materially bigger blast radius, and existing paired users with a few missing rows shouldn't have their analysis silently rerouted. `design="unpaired"` forces the new path explicitly regardless of detection.
- `GroupComparisonResult.summary()` using reused `_gradient_interval_line` + a new minimal pairwise-table printer (showing both the CI and the Holm-corrected p-value per pair) + inline alignment disclosure (§3.6).
- No `.plot()` yet (deferred to Phase 2).
- A basic synthetic Monte Carlo calibration check for the Bonferroni-corrected pairwise CIs, **including a specific check for the binary family's t-interval-on-proportions boundary behavior** (§5) — does it produce out-of-range CIs at realistic eval sample sizes, and if so does it need clipping or just a documented caveat? Following the existing convention (`simulations/harness/cases/pvalues.py --mode ppi`/`simultaneous_ci`) — doesn't need to be as exhaustive as the paired path's validation suite, but should confirm nominal coverage isn't badly broken, per this codebase's evident house standard of not shipping unvalidated CI machinery silently.
- `pytest` coverage: new `tests/test_unpaired.py` covering the routing table (binary vs. everything-else families), PPI on/off, `design=` opt-in behavior (auto/paired/unpaired, including the new error path), the synthetic-item-column fallback, and `to_dict()`/`to_frame()`.
- Rewrite the paper's App Store/FlipFlop PPI scenario against this, replacing the synthetic-item-index hack — this was the original motivating case and is the best end-to-end validation.

**Phase 2 (nice-to-have).**
- `.plot()` (bespoke minimal renderer per §3.6).
- Multi-factor/factorial between-subjects support (out of scope for Phase 1, see §6).
- Šidák (in place of Bonferroni) for the pairwise CI axis, gated on an actual calibration sweep confirming it's valid for this bootstrap's dependence structure.

**Phase 3 (nice-to-have, exploratory).**
- Investigate real forest.py-compatible adapter (an `entity_stats`/`pairwise`-shaped shim) so `GroupComparisonResult` could optionally reuse `plot_ci_forest` directly instead of a bespoke renderer — larger effort, deferred until Phase 2's bespoke plot proves insufficient.

## 5. Decided (after review) vs. still open

**Decided, not open anymore:**
- **Auto-route vs. explicit opt-in** → explicit opt-in (`design=`), required for Phase 1. See §4. This was the single highest-blast-radius risk in the plan (silently changing which statistical engine runs on existing users' data) and didn't need to stay open.
- **CI correction: Šidák vs. Bonferroni** → Bonferroni now (§3.4), Šidák later once validated (moved to Phase 2). No longer blocks Phase 1.
- **p-value correction** → Holm, as a second axis alongside the CI correction (§3.4), reusing the existing `correct_pvalues(method="holm")` helper. New decision, not previously in the plan.
- **`GroupComparisonResult` location** → `core/unpaired.py`, re-exported from `api.py`. Matches the existing `MultiModelBundle` convention (lives in `core/`, re-exported); low-stakes enough not to need further deliberation.
- **`to_dict()`/`to_frame()` timing** → Phase 1, not deferred. Confirmed: evalstats is a library API, not just a reporting tool, so programmatic export matters as much as `.summary()`.
- **Data-type routing, fully decided, two families not four**: binary (k=2 and k≥3) → `anova_oneway`/`ttest` (Δp, Welch's) — a deliberate patch given no PPI-corrected chi-square/Fisher's-exact exists, with an acknowledged t-interval-on-proportions boundary-behavior risk (see below). Everything else — continuous, likert, grade (k=2 and k≥3) → `kruskalwallis`/`mannwhitney` (θ dominance), uniformly, not split further by type. This also resolves the former "k=2 likert" open question — likert now falls under the same "everything else" rule as continuous/grade, no separate case.

**Still genuinely open, needs a human call:**
- **`"grade"` score type routing (§3.2)** — treating it as `continuous` (and thus routing to the `kruskalwallis`/`mannwhitney` family) is a reasonable, low-risk default for now; a percentage grade could plausibly warrant its own `AUTO_UNPAIRED_METHOD_TABLE` row later. Not worth more design time before real data motivates it.
- **New: t-interval-on-proportions boundary behavior for the binary family** — the `anova_oneway`/`ttest` patch for binary data can, in principle, produce CIs outside `[0,1]`/`[-1,1]` at extreme proportions or small N (the exact reason the *paired* path uses Tango instead of a generic t-interval for binary data, and there's no between-subjects Tango equivalent today). Needs a concrete check during Phase 1's calibration testing (does it actually happen in practice at realistic eval sample sizes? does it need clipping, or a documented caveat?) — not a blocker to starting, but a specific thing Phase 1 must verify, not assume away.

## 6. Explicit non-goals

- **Multi-model / factorial between-subjects designs** (`compare(factors=["model","prompt"])`-equivalent for unpaired data) — not attempted. `MultiModelBundle`/`analyze_factorial`'s LMM path have no between-subjects analog scoped here; this plan is single-factor only, matching `evalstats.tests`' own current scope (`ttest`/`mannwhitney`/`anova_oneway`/`kruskalwallis` are all single-factor).
- **Mixed designs** (some factors paired, some unpaired within the same comparison — e.g. within-subject prompt variation crossed with between-subjects app assignment) — not attempted; genuinely different statistical machinery (a mixed-model with both fixed within- and between-subject terms), out of scope.
- **Seeded/multi-run (R≥3) between-subjects benchmarks** — `evalstats.tests` functions have no run-axis concept at all; not attempted here, same scoping precedent as PPI's own existing seeded-benchmark exclusion (`api.py`'s `_run_alignment_ppi` already refuses seeded benchmarks outright).
- **Full `plot_ci_forest`/`ComparisonResult` API parity** — deferred to the exploratory Phase 3; Phase 1–2 ship a narrower, purpose-built reporting surface (per-group means + flat pairwise table, no executive summary/rank bands/forest brackets — see the scope correction in §1).
- **A true Tukey-HSD-style joint mean-difference post-hoc for continuous data** — explicitly not attempted; Q2's finding is that Kruskal-Wallis's θ_ab post-hoc covers the k≥3 case for continuous/likert/grade instead, by design, to avoid unvalidated new statistical derivation. (This is distinct from the binary family's `anova_oneway` + repeated Bonferroni/Holm-corrected pairwise `ttest` — that's a legitimate, different, already-standard post-ANOVA procedure, not Tukey's studentized-range method, and it *is* in scope per §3.2.)
- **Rewriting the paper's App Store/FlipFlop scenario itself** — this plan enables it but doesn't do the rewrite; that's separate paper-writing work gated on Phase 1 landing.
- **`evalstats label` CLI changes** — `_detect_paired`'s relocation (Phase 0) is a pure refactor; no behavior change to the labeling CLI is in scope.
